# TreeWork — 서울 공공기관 수목·나무의사 공고 수집기

서울시와 24개 자치구의 고시공고·채용공고를 하루 2회 수집해 수목·나무의사 관련
공고만 텔레그램으로 보낸다. 별도 서버 없이 GitHub Actions에서 돌아간다.

```bash
python main.py --dry-run        # 발송 없이 확인
python selftest.py --dry-run    # 파서가 살아있는지만 점검
```

---

## 왜 '나무의사'로 검색하면 안 되는가

이 프로젝트의 설계는 전부 아래 실측 결과에서 나왔다. 서울시 일자리포털
공공일자리 **4년치 3,826건**의 제목을 전수 검색한 결과(2026-08-04):

| 키워드 | 건수 | | 키워드 | 건수 |
|---|---:|---|---|---:|
| `나무의사` | **0** | | `녹지` | 36 |
| `수목치료기술자` | **0** | | `공원녹지` | 18 |
| `수목진료` | **0** | | `수목` | 17 |
| `예찰` | **0** | | `조경` | 8 |
| `가로수` | **0** | | `산림` | 6 |

**'나무의사'로 필터링하면 4년 내내 0건이 나온다.** 실제 공고 제목은 이렇게 생겼다.

- `[북부공원여가센터] 2024년 기간제노동자(산림병해충방제) 채용 공고`
- `서울역사박물관 기간제근로자 채용 공고(녹지관리원)`
- `노원구 시간선택제임기제공무원 다급(산림재난 대응단 운용 분야) 채용계획 공고`
- `금천구 시간선택제 임기제공무원(라급, 공원녹지분야) 경력경쟁임용시험 공고`

'나무의사'와 '수목치료기술자'는 **직무명이 아니라 자격 요건**이고, 대체로 HWP
첨부파일 안에만 등장한다. 그래서 이 수집기는

1. 제목을 **넓게** 걷고 (`treework/filters.py` 의 3단 티어)
2. 상세·첨부에서 A티어가 잡히면 **등급을 올리고**
3. 담당부서가 `푸른도시과`·`공원녹지과`·`조경과` 등이면 제목에 키워드가 없어도
   **확인필요로 올린다** (안전망)

누락 방지가 목표이므로 **과잘림보다 과보고**를 택한다. 노이즈 키워드는 후보를
버리지 않고 등급만 낮춘다.

### 티어

| 티어 | 성격 | 매칭 범위 |
|---|---|---|
| 🔴 A | `나무의사` `수목치료기술자` `산림병해충` `예찰방제` `재선충` … | 제목·부서·본문·첨부 |
| 🟡 B | `녹지관리` `가로수` `방제단` `공원녹지` `조경분야` … | 제목·부서·본문·첨부 |
| ⚪ C | `조경` `녹지` `산림` `수목` `나무` `숲` … | **제목·부서만** |

C를 본문까지 허용하면 페이지 메뉴·푸터·안내문에 `조경/녹지/나무`가 널려 있어
거의 모든 공고가 걸린다(실측 확인). `정원`은 키워드에서 **제외**했다 —
채용공고에 `정원 5명`(TO)으로 상시 등장해 쓸 수 없다. 대신 `정원사`를 B에 둔다.

## 수집 대상 (40개 소스, 서울시 + 24개 구 + 나라장터)

| kind | 대상 | 방식 |
|---|---|---|
| `seoul_job_portal` | 서울시 일자리포털 공공일자리 | POST, 200건/요청 |
| `seoul_notice` | 서울시 고시·공고 | GET, 2페이지 |
| `eminwon` | 자치구 8곳 공통 고시공고 시스템 | POST |
| `generic_table` | 자치구 16곳 자체 게시판 | GET + 범용 파서 |
| `g2b_bid` | 나라장터 용역입찰 | Open API, 키워드별 질의 |

### 나라장터를 넣은 이유

나무의사 실수요는 채용보다 **용역 발주**로 나오는 경우가 많다.
`○○구 생활권 수목 진단 및 진료 용역`, `가로수 병해충 예찰방제 용역` 처럼.
채용공고와 달리 용역은 **공고명 자체가 서술적**이라 공고명 키워드 검색이 잘
듣는다. 그래서 전국 용역을 전량 끌어오지 않고 키워드 15개로 질의한 뒤
공고기관·수요기관 이름에 '서울'이 있는 건만 남긴다.

`G2B_SERVICE_KEY` 가 없으면 이 소스만 **'건너뜀'** 으로 처리되고 경고를 띄우지
않는다 — 미설정과 고장을 구분하지 않으면 경고 피로가 생겨 진짜 고장을 흘려보게 된다.

### 서울시 일자리포털이 최우선인 이유

서울시 본청 전 부서 + 사업소 + 산하기관/재단/민간위탁 채용을 한 곳에 모으고,
목록에 마감일이 이미 들어 있다. **단 자치구는 포함되지 않는다** — 그래서 구청을
따로 긁는다.

### 자치구는 왜 파서가 두 종류인가

25개 구청 CMS가 최소 6종으로 갈려 있다(`portal/bbs/list.do`, `selectEminwonList.do`,
`selectBbsNttList.do`, `Contents.asp`, `site/<구>/ex/...`, 자체 JSP). 25개 셀렉터를
하드코딩하는 대신,

- **eMinwon 공통 시스템**을 쓰는 8개 구는 단일 POST 파서로 처리
- 나머지는 **범용 테이블 파서** 하나로 처리 (`collectors.parse_table`)

범용 파서의 핵심은 **날짜 밀도 게이팅**이다. 진짜 게시판 목록은 행마다 날짜가
있고, 부서 목록이나 관련기관 링크 모음에는 없다. 날짜 있는 후보가 하나도 없으면
**빈 리스트를 돌려 실패로 처리**한다 — 엉뚱한 링크 모음을 공고로 착각해 발송하는
것보다 0건 경고가 낫다.

이 방식은 CMS가 개편돼도 테이블 구조만 유지되면 계속 작동한다. 하드코딩
셀렉터보다 개편에 훨씬 강하다.

## 사이트가 바뀌거나 막히면 어떻게 되는가

이 시스템의 최대 실패 모드는 크래시가 아니라 **조용한 0건**이다. 사이트가
개편돼 파서가 깨져도 `try/except` 로 다 삼키면 매일 "신규 없음"이 오고, 사용자는
"요즘 공고가 없구나" 하고 몇 달을 넘긴다. 그래서 4중으로 막는다.

| 층 | 감지 대상 | 동작 |
|---|---|---|
| 1 | 소스가 예외를 던짐 | 소스별로 기록 → 텔레그램 ⚠️ 경고. **3회 연속이면 🚨로 승격** |
| 2 | 정상 응답인데 0건 | 「구조 변경 유력」 경고. 구조 변경의 가장 흔한 신호 |
| 3 | **수집량 급감** | 과거 중간값의 40% 미만이면 경고. `status=ok`이고 0건도 아닌 **부분 파싱 실패**를 잡는 유일한 장치 |
| 4 | 스크립트 자체가 죽음 | 워크플로우 `if: failure()` 단계가 직접 curl로 발송. 스크립트가 죽으면 스크립트는 알릴 수 없다 |

'미설정'(`skipped`)은 경고에 섞지 않는다. API 키를 아직 넣지 않은 상태를 고장으로
알리면 경고 피로가 생겨 진짜 고장을 흘려보게 된다.

여기에 더해

- **주 1회 자기 점검** (`selftest.py`): 공고가 없는 조용한 주에도 39개 소스가
  실제로 파싱되는지 확인한다. 공고 유무와 파서 생존을 분리해서 본다.
- 소스별 이력은 `seen.json` 의 `health` 에 누적된다 (마지막 정상일, 연속 실패
  횟수, 최근 10회 수집량).
- 신규 0건이고 문제도 없으면 `✅ 정상 동작 · 신규 공고 없음`을 보낸다.
  **침묵이 곧 정상이 되지 않게** 한다.

### 실제로 고칠 때

경고가 오면 `sources.yml` 에서 해당 소스의 URL을 열어본다. URL이나 게시판
번호만 바뀐 경우가 대부분이고, **코드를 고칠 필요 없이 YAML 한 줄만 수정**하면
된다. 소스 정의가 전부 외부화되어 있는 이유다.

구조가 근본적으로 바뀌었으면 해당 소스만 `enabled: false` 로 내리고 나머지를
계속 돌린다. 한 소스의 실패가 전체를 멈추지 않는다.

### 막히는 경우 (IP 차단)

GitHub Actions 러너는 해외 Azure IP를 쓴다. 일부 구청 WAF가 이를 막을 수 있다.
실측에서 **강북구는 봇 핑거프린팅(`sabFinge` 쿠키)** 을 걸어두고 있어 홈페이지
직접 접근이 불안정했다 — eMinwon 경로로 우회해 해결했다.

403/429 가 반복되면 경고 메시지에 그 사실이 드러난다. 대응 순서는

1. 해당 소스만 `enabled: false` 로 내려 나머지를 보호
2. 우회 경로 확인 (강북구처럼 eMinwon 경로가 있는 경우가 많다)
3. 그래도 안 되면 그 소스만 국내 IP에서 실행 — 개인 PC 작업 스케줄러나
   국내 무료 티어 VM. 나머지는 Actions에 그대로 둔다

### 이미 반영된 방어

- **SSL 폴백**: 인증서 체인이 낡은 사이트(실측: 노원·강남·강북·금천·양천
  eMinwon)는 해당 호스트에 한해 검증을 낮춰 재시도하고, 낮춘 사실을 로그에 남긴다
- **인코딩 폴백**: `charset` 헤더가 없거나 틀린 구청에 대해 utf-8 → euc-kr → cp949
- **재시도**: 5xx/타임아웃은 재시도, 4xx는 즉시 포기(재시도 무의미)
- **요청 간격 1.2초**: 공공 사이트 부하와 차단 회피
- **중복 키가 링크 비의존**: `sha1(소스ID|정규화제목|등록일)`. URL 파라미터
  구조가 바뀌어도 재발송하지 않는다
- **발송 실패 시 상태 저장 안 함**: 텔레그램 발송이 실패한 공고를 '보낸 것'으로
  기록하면 영구 누락이 된다. 저장을 건너뛰고 다음 실행에서 재시도한다
- **손상된 `seen.json` 은 비우지 않고 실패**: 조용히 초기화하면 전체가 미발송
  상태로 되돌아가 대량 재발송이 일어난다

## 설치

1. 저장소를 만들고 이 파일들을 넣는다 (Public 이면 Actions 무료 무제한)
2. 텔레그램 봇 생성: [@BotFather](https://t.me/BotFather) → `/newbot` → 토큰 받기
3. 봇과 대화를 시작한 뒤 `chat.id` 확인 — **국내에서는 아래 "국내 네트워크" 참고**
4. 저장소 **Settings → Secrets and variables → Actions** 에 등록

   | 이름 | 필수 | 값 |
   |---|---|---|
   | `TELEGRAM_BOT_TOKEN` | ✅ | BotFather가 준 토큰 |
   | `TELEGRAM_CHAT_ID` | ✅ | 위에서 확인한 chat id |
   | `G2B_SERVICE_KEY` | 선택 | 나라장터 API 키 (아래 참고) |

5. **Actions 탭 → 수목 공고 수집 → Run workflow** 로 수동 1회 실행해 확인

### 국내 네트워크에서 chat_id 를 못 가져올 때

국내 ISP에서 `api.telegram.org` **TCP 443 접속이 차단**되는 경우가 있다.
실측(2026-08-04): DNS는 정상 해석(`149.154.166.110`)되지만 TCP 연결이 실패하고
브라우저는 `ERR_CONNECTION_TIMED_OUT` 을 낸다. 유선·모바일 모두 동일했다.
텔레그램 **앱은 정상 작동**한다(다른 프로토콜을 쓴다).

> **이 차단은 시스템 동작에 영향이 없다.** 발송은 GitHub Actions 러너(해외 IP)가
> 하고, 알림은 앱으로 정상 수신된다. 막히는 것은 최초 `chat_id` 조회 한 번뿐이다.

두 가지 우회 방법:

**방법 A — 봇으로 확인 (즉시, 앱만 사용)**
텔레그램 앱에서 [@userinfobot](https://t.me/userinfobot) 에 `/start` 를 보내면
본인의 숫자 ID가 온다. **1:1 대화의 `chat_id` 는 본인 사용자 ID와 같다.**

**방법 B — Actions 에서 조회 (발송 경로까지 검증)**
`.github/workflows/telegram-setup.yml` 이 이 용도로 들어 있다.

1. Secret `TELEGRAM_BOT_TOKEN` 만 먼저 등록
2. 텔레그램 앱에서 **본인 봇에게 아무 메시지나 보낸다** (안 보내면 조회 결과가 빈다)
3. Actions 탭 → **텔레그램 설정 도우미** → Run workflow
4. 로그와 실행 요약에 나온 `chat_id` 를 Secret `TELEGRAM_CHAT_ID` 로 등록

방법 B는 봇 토큰 유효성, chat_id, 실제 발송까지 한 번에 확인한다. 테스트 메시지가
앱에 도착하면 배포 경로에 문제가 없다는 뜻이다.

> Public 저장소는 Actions 로그가 공개된다. `chat_id` 만으로는 아무것도 할 수 없지만
> (봇 토큰이 있어야 한다) 신경 쓰이면 확인 후 실행 기록을 삭제하거나 이 워크플로우
> 파일을 지워도 된다. 설정이 끝나면 더 필요 없다.

로컬에서는 `--dry-run` 으로만 테스트할 수 있다(실제 발송은 차단됨). 수집·필터링
로직 확인에는 충분하다.

### 나라장터 API 키 (선택, 권장)

1. [공공데이터포털](https://www.data.go.kr) 회원가입
2. **"입찰공고정보서비스"** 검색 → 조달청 제공 건 → **활용신청** (자동 승인)
3. 마이페이지 → 개발계정 → **일반 인증키(Decoding)** 복사
   > ⚠️ **Decoding 키**를 써야 한다. Encoding 키를 넣으면 `%2B` 가 `%252B` 로
   > 이중 인코딩되어 인증에 실패한다.
4. Secret `G2B_SERVICE_KEY` 로 등록

키 발급 후 아래로 즉시 검증할 수 있다.

```bash
G2B_SERVICE_KEY=발급받은키 python main.py --dry-run --source g2b-servc
```

- 정상: 서울 소재 기관의 용역 공고가 나오거나 `신규 공고 없음`
- 키 문제: `API 오류: SERVICE_KEY_IS_NOT_REGISTERED_ERROR` → 승인 대기(최대 1시간)
  또는 Encoding 키를 잘못 넣은 경우

첫 실행은 최근 21일치를 전부 신규로 보므로 메시지가 여러 건 올 수 있다.

### 스케줄

`0:07`, `6:07` UTC = **09:07, 15:07 KST**, 하루 2회. 정시를 피한 이유는 Actions
스케줄이 정시에 전 세계 작업과 몰려 지연·스킵되기 때문이고, 하루 2회인 이유는
자치구 기간제 공고의 접수기간이 3~5일로 짧기 때문이다.

> Public 저장소는 60일간 저장소 활동이 없으면 스케줄이 자동 정지된다. 이 작업은
> 매일 `seen.json` 을 커밋하므로 사실상 해당되지 않는다.

- ⚠️ 상세요강 필드가 **대부분 비어 있고 내용이 `.hwpx` 첨부에만** 있다

**서울시 고시·공고**
- `bbsNo=277`, 페이징 `cntPerPage`(최대 50)`&curPage`
- 목록 `table.sib-lst-type-basic tbody tr`, 상세 `?bbsNo=277&nttNo=<n>`
- 본문 `div#scrabArea` — **HWP가 HTML로 변환되어 전문이 실린다** (첨부 파싱 불필요)
- ⚠️ **사이트 자체 검색은 쓸 수 없다.** 12,129건 중 '수목' 검색이 6건뿐이고

  로컬 필터가 유일한 방법

**eMinwon (자치구 공통)**
- `POST https://<sub>.eminwon.seoul.kr/emwp/gov/mogaha/ntis/web/ofr/action/OfrAction.do`
- `method=selectListOfrNotAncmt`, `methodnm=selectListOfrNotAncmtHomepage`,
  `jndinm=OfrNotAncmtEJB`, `context=NTIS`, `homepage_pbs_yn=Y`, `subCheck=Y`
- `not_ancmt_se_code`: **01(고시)과 04(공고)만 실제로 존재**하고 02/03/05/06/07은
  0건. 채용공고는 **04에 들어 있다**
- 상세는 POST 전용(`method=selectOfrNotAncmt`) → **공유 링크를 만들 수 없어**
  링크는 구청 게시판으로 대체한다
- ⚠️ 목록 제목이 잘린다(`...(산림재난 대응단 운용 분야) 채...`). 잘린 뒷부분에
  키워드가 있을 수 있어 표적 상세 조회로 전체 제목을 복원한다
- ⚠️ 번호 셀도 `<a>` 라서 첫 앵커를 쓰면 제목이 `"219"` 가 된다. 가장 긴 앵커를 써야 한다
- 작동 확인: 강남·강북·금천·노원·도봉·동작·서초·양천 (8/25)

**나라장터 입찰공고 API**
- 유효 엔드포인트는 **`/1230000/ad/BidPublicInfoService/`** 하나뿐이다.
  구버전 `BidPublicInfoService04` `05` `06` 은 전부 `NO_OPENAPI_SERVICE_ERROR`(폐기)
- 확인된 오퍼레이션: `getBidPblancListInfoServc`(용역),
  `getBidPblancListInfoServcPPSSrch`

  `check_status=False` 로 호출해 본문의 `errMsg` 를 경고에 실어 보낸다
  (그러지 않으면 `HTTPError: 403` 만 남아 원인을 알 수 없다)
- 날짜 파라미터는 `YYYYMMDDHHMM` 형식(`inqryBgnDt`/`inqryEndDt`), `inqryDiv=1` 은

## 아직 넣지 않은 채널

아래는 접근 가능은 확인했으나 **구조 검증을 하지 않아 넣지 않았다.** 검증 없이
추측 셀렉터를 넣으면 매일 조용히 0건을 반환하면서 성공으로 보고하게 되고,
그것이 이 프로젝트가 가장 피하려는 실패 모드다.

| 채널 | 상태 | 비고 |
|---|---|---|
| 클린아이 잡플러스 | 미구현 | 접근 OK. 지방공사·공단·출연기관(서울시설공단, SH 등) |
| 잡알리오 | 미구현 | 접근 OK. 공공기관 채용 통합 |
| 나라일터 | 보류 | `www.gojobs.go.kr/mainIndex.do` 로 이전. 완전 SPA라 정적 스크레이핑 불가 |
| 성북구 | 보류 | 도메인 불통 |

나라장터는 구현했다. 다만 **서비스키가 있어야 실동작을 확인할 수 있다** —
엔드포인트 생존과 오류 처리 경로는 검증했지만(아래 검증 기록), 응답 필드명은
공식 스펙 기준으로 작성했고 실데이터로 확인하지 못했다. 키를 넣고 처음 실행할 때
0건이 나오면 `-v` 로 응답을 확인해 필드명을 맞춰야 할 수 있다.

## 알려진 한계

- eMinwon 8개 구와 서대문·종로는 상세 직접 링크를 만들 수 없어 게시판 URL로
  안내한다 (메시지에 `직접 링크 없음`으로 표시)
- 강북·금천은 게시판 URL을 확정하지 못해 구청 홈페이지로 링크한다
- 구형 `.hwp`(바이너리)는 미리보기 텍스트만 추출된다. 부분 판독일 때 메시지에
  `첨부 일부만 판독`으로 표시한다
- 자치구 `generic_table` 소스는 1페이지(10건)만 본다. 하루 2회 실행이라 충분하지만
  공고가 폭주하는 날에는 이론상 누락 가능 → 급감 감지가 아니라 **증가**를 잡는
  장치는 없다
